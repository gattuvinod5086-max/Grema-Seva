01 — Where the code actually stands

Two apps are living in one repo

GramSeva today is not one prototype, it is two, and they do not share a line of state. Understanding this split is the whole job, because the backend work is mostly deciding which of the two survives.

Track A — the Terminal app at /app

This is the flow that looks finished: onboarding, OTP screen, report form, issue list, officials' dashboard, news, emergency contacts, Krishi and Vikas assistants. It runs entirely in the browser. The database is MockDB in src/react-app/data/terminalData.ts, the session is a localStorage key, and the OTP is a literal string compared client-side. Nothing survives a cleared browser, and nothing is visible to anyone else. This is a demo in the strict sense.

Track B — the web app at /, /telangana

This one is genuinely server-backed: Hono on Cloudflare Workers, D1 for data, R2 for photos, Google OAuth for login. It has real SLA computation, escalation, an audit trail, citizen confirmation and analytics. It is roughly 1,800 lines and it is better than it looks. But it is reachable only through the Mocha auth provider, its login path is half-migrated to direct Google OAuth, and its authorization has holes wide enough that "data isolation is must" is currently not true of it.

The good news, and it is substantial: the domain logic in src/shared/services/ — SLA clocks, escalation ladders, issue classification, department routing, duplicate detection, village scoring, audit formatting — is written against plain objects with no platform dependency. Those eleven files move to the new backend unchanged. The thinking is done; it is the plumbing that has to be rebuilt.

02 — What the review turned up

Findings, worst first

Every location below was read, not inferred. Line numbers are against main as of this review.

01

CriticalEvery citizen can read every neighbour's complaint

When a citizen has a village set, the issue list query becomes SELECT * FROM issues WHERE village = ? with no owner filter, and canViewIssue ends with a blanket "same village, allow". A resident of Kondapur can read the full text, photo, GPS coordinate and reporter ID of every complaint filed in Kondapur — including a domestic dispute, a caste harassment report, or a complaint against a neighbour.

This may in fact be an intentional transparency feature. It is not written down anywhere, there is no per-report visibility control, and the citizen is never told. That makes it a leak either way. This is the single most important product decision on the list.

03 — What wasn't on your list

The gaps between your five features and a working system

You named SMS OTP, Google login, report routing, status visibility, official updates, data isolation and map location. Those are the right seven. Here is what sits between them that nothing in the repo currently covers.

There is no directory of who the officials actually are

"The report goes to the sarpanch" needs a table that answers who is the sarpanch of this village, right now. That table does not exist. departmentRouting returns a department name as a string; assigned_to_user_id is only ever set by a human clicking assign. Auto-routing is impossible until officials are modelled with a jurisdiction and a validity period — terms end, officials transfer, and the audit trail has to still make sense afterwards.

Location is free text, so isolation is built on string equality

District, mandal and village are TEXT columns on both users and issues, and every access decision compares them with =. One trailing space, one "Kondapur" vs "Kondapuram", and a complaint becomes invisible to the person who should see it — or visible to someone who shouldn't. These need to be foreign keys into a canonical jurisdiction table seeded from the LGD codes.

Nobody gets told anything

The entire loop you described — citizen reports, sarpanch acts, citizen sees progress — has no notification layer. The sarpanch learns about a complaint by opening a dashboard; the citizen learns their issue was resolved by opening the app. Once MSG91 is wired for OTP the same channel carries status SMS, and it needs its own DLT templates registered in Telugu and English, which is a lead-time item.

Consent, retention and residency are unaddressed

This app collects phone numbers, father's names, GPS coordinates and photographs of identifiable people, on behalf of a government body. Under the DPDP Act 2023 that needs a consent record, a stated purpose, a retention period and a deletion path — none of which exist. It also very likely needs to sit in an Indian region, which constrains the hosting choice below.

Smaller pieces with no home yet

  • Voice notes — VoiceInput exists in the UI; there is no attachment model to store what it captures.
  • Multiple photos — before/after evidence needs a row per file, not one column.
  • Moderation — no way to withdraw, hide or flag an abusive complaint, and no soft delete.
  • Search and export — officials will ask for both within a week of launch.
  • Language — translations exist client-side, but SMS and notification language is a per-user setting that isn't stored.
  • Offline queue — offlineSync.ts models sync state; the server has no endpoint to accept a batch of queued reports.
  • Repo hygiene — twelve FIX_* / START_HERE markdown files and eight shell scripts in the project root, largely superseded.

05 — Data model

What Postgres adds

Beyond a straight port of the eleven existing tables. The first four are what make auth and isolation structural rather than remembered.

TableCarriesWhy it earns a table
jurisdictions district, mandal, village, ward, LGD code, centroid Canonical geography. Every user, issue and official points at a row here instead of comparing strings.
official_assignments user, role, jurisdiction, department, valid_from / valid_to Answers "who is the sarpanch of this village today" — the lookup auto-routing needs, and the one that keeps history correct after a transfer.
auth_identities user, provider, provider_uid, verified_at One citizen, two login methods. Lets a phone-OTP account and a Google account resolve to the same person instead of two.
otp_requests phone, code_hash, purpose, attempts, expires_at, consumed_at, ip Hashed codes, 5-minute expiry, capped attempts, per-phone and per-IP throttles. Never stores the code in clear.
sessions user, token_hash, device, ip, expires_at, revoked_at Makes logout mean something, and lets an official's session be revoked when their term ends.
issue_attachments issue, kind (photo / voice), key, mime, bytes, phase Multiple files, and the before/after evidence pairing officials will want for proof of work.
notifications user, channel, template, payload, status, provider_msg_id One queue behind SMS, push and in-app, with delivery state you can actually debug.
sms_log phone, dlt_template_id, provider_msg_id, status, cost DLT compliance evidence and a running cost line. You will want this the first time a bill surprises you.
consents user, purpose, version, granted_at, withdrawn_at DPDP Act record of what each citizen agreed to and when.
audit_log actor, action, entity, before, after, ip Generalises today's issue_updates so role changes and official reassignments are recorded too.

Columns onto issues

jurisdiction_id, geom geography(Point,4326) with a GiST index, accuracy_m, address_text, reported_via, visibility, idempotency_key (unique), duplicate_of_id, withdrawn_at.

On data isolation specifically. The five critical findings above are all the same failure: authorization written by hand in each handler, and eventually forgotten in one. Postgres row-level security fixes the category rather than the instances — policies on issues, users and attachments keyed to a per-request SET LOCAL app.user_id / app.role / app.jurisdiction, so a handler that forgets its WHERE clause returns nothing instead of returning everything.

That is the strongest reason Postgres was the right call over staying on D1, which has no equivalent.

06 — Delivery

Six phases

Ordered by dependency, not by appetite. Phase 0 ships to the current Cloudflare deployment on day one, because the rewrite takes weeks and the leaks are live now. Estimates assume one developer.

01–2 days

Stop the bleeding on what's deployed

Patches to the existing worker, shipped before any restructuring begins.

  • Identify and purge the PDF from public/ and from git history; gitignore the .deb
  • Put auth and an ownership check on /api/files/:key
  • Delete PATCH /api/users/:id/role or restrict it to admin with a role allowlist
  • Fix the analytics guard; scope sarpanch writes to their own village
  • Lock CORS to known origins; scope and paginate /api/users
→ nothing sensitive is publicly readable
13–4 days

Monorepo and API skeleton

The move, with no behaviour change, so the diff stays reviewable.

  • Workspaces; src/react-app → apps/web, src/shared → packages/shared
  • apps/api on Hono + Node adapter; Drizzle over Postgres; docker-compose for local Postgres/PostGIS/MinIO
  • Port the eleven tables as migration 001 — reconstructing what the missing migrations 3 and 4 did
  • Config validation on boot, structured request logging, one error shape, health endpoint
→ existing endpoints answer from Postgres
24–5 days

Real authentication

Phone OTP and Google resolving to one identity, with sessions you can revoke.

  • MSG91 adapter behind an SmsProvider interface, with a console driver so the flow is testable before DLT clears
  • POST /auth/otp/request and /verify — hashed codes, 5-min expiry, 5 attempts, throttled per phone, per IP and per day
  • Google OAuth with state, verified id_token, email_verified enforced, and its own SESSION_SECRET
  • Account linking on matching verified phone or email; server-side sessions with real logout
  • Retire Mocha and the authMiddleware / requireAuth split; one middleware everywhere
→ OTP arrives on a real handset
33–4 days

Isolation as structure

The phase that makes "data isolation is must" true rather than intended.

  • Seed jurisdictions from LGD codes; migrate the text columns to foreign keys
  • official_assignments with validity windows; role and scope resolved once per request
  • RLS policies on issues, users and attachments, driven by SET LOCAL session variables
  • A contract test suite that asserts each role sees exactly its own slice — the regression net for every finding above
  • Settle and implement the complaint-visibility decision (private / village-public / opt-in per report)
→ a forgotten WHERE clause returns nothing, not everything
45–6 days

The complaint lifecycle, end to end

Report reaches the right official, citizen watches it move, official reports progress.

  • Create in one transaction: text, attachments, location, idempotency key, server-side duplicate check
  • Auto-route on category and jurisdiction to a named official, with escalation targets resolved from the same table
  • Status and progress updates with mandatory evidence on resolve; citizen confirm / reopen; full audit
  • SLA escalation moved to a scheduled job; notification queue with SMS and in-app, Telugu and English
  • Paginated, filterable list endpoints for citizen and official views
→ the loop you described actually closes
53–4 days

Map and geography

Leaflet on OpenStreetMap tiles — no key, no billing, no vendor lock.

  • Pin-drop and GPS capture on the report form, with accuracy shown and manual correction
  • Reverse geocode to an address and a jurisdiction suggestion; Nominatim results cached server-side to stay inside its usage policy
  • Officials' map view: clustered pins, severity colouring, heatmap over the existing toMapPoints
  • PostGIS radius query feeding duplicate detection — "three reports of this pothole within 50 m"
→ location is data, not a text field
64–5 days

Hardening and go-live

  • Rate limits across auth, create and upload; upload size, MIME and EXIF handling
  • Integration tests on auth, isolation and the issue lifecycle; CI on every push
  • Consent capture, retention policy, deletion path, privacy notice
  • Backups with a tested restore, error tracking, uptime checks, runbook
  • Load check at a district's volume; staging environment mirroring production
→ ready for a real village

Roughly 23–30 working days for one developer, five to six calendar weeks. Phases 0 and 1 are independent of every external dependency below and can start immediately.
